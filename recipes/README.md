# Recipes

`verify.sh` 是每一份的重點。它不檢查你的程式碼長什麼樣（那種檢查換個寫法就失效），
它檢查**行為**：打得穿還是打不穿。

有四種型別，差別在「要修的是什麼」。四種的 `verify.sh` 都是**並排跑兩版**，
不是只跑修好的那版：只會綠的腳本證明不了洞是真的。

## 修程式碼的

```
NN-做什麼/
├── README.md      問題、為什麼會發生、怎麼修、什麼情況不適用
├── before/        有洞的版本
├── after/         修好的版本
└── verify.sh      同一支腳本裡跑兩版，印出它們的行為差在哪
```

`01-frontend-api-key` 是這一型。想當練習題就改 `before/` 再跑一次，
看有洞那半的數字有沒有掉到 0。

## 修檢查方法的

有些題目要修的不是程式碼，是你驗證的方式。這種沒有 `before/`，
因為 before 與 after 都是同一支腳本裡的兩種寫法：

```
NN-做什麼/
├── README.md      每個情境在測什麼、naive 錯在哪
└── verify.sh      每個情境跑兩次，naive 給你假通過，fixed 才是對的
```

`02-secret-scan-blind-spots` 與 `03-revoke-verification` 是這一型。判準沒有變：
跑出來的東西要能分辨對錯，而不是看程式碼長相。

這一型還要再過一關：**naive 那半必須真的重現假通過。**
只有 fixed 會綠的腳本證明不了 naive 錯在哪，而那正是這種 recipe 唯一要說的事。

## 換地方跑同一支腳本的

第三型只有一支腳本，不改它，改的是它跑在哪裡：

```
NN-做什麼/
├── README.md         這一節在比什麼、為什麼要有對照組
├── suspect.sh        全程不變的那支
├── Dockerfile        關它的地方
├── flags.sh          唯一一份旗標清單，下面兩支都 source 它
├── run-isolated.sh   讀者複製去自己用的那支
└── verify.sh         本機一次、關起來一次，比「它碰得到什麼」
```

`flags.sh` 不是為了整齊。旗標兩邊各抄一份的時候，把 `run-isolated.sh` 的刪光
`verify.sh` 照樣滿分，於是「驗證過生效」講的不是讀者手上那一份。
複製這一型出去的時候三支要一起帶走。

`06-run-it-somewhere-else` 是這一型。它多一條規矩：
**每一條「找不到」都要配一條「找得到」。** 「容器裡讀不到那些檔案」在檔案本來
就不存在、腳本沒跑起來、掛載沒生效的時候通通也會成立。所以本機一條都讀不到要報紅，
而容器那一發要先證明腳本真的跑完了，網路那條要先證明不加旗標時連得出去。

## 查它存不存在的

第四型連要不要跑那支腳本都還沒決定，先去外面問一個問題，
所以沒有 before/after，也沒有 naive/fixed，兩版對照長在查詢本身：

```
NN-做什麼/
├── README.md      在問什麼、對照組為什麼是地基、邊界到哪
├── check-*.sh     去問的那支，開頭先跑一組正反對照才敢報答案
├── verify.sh      每一節都是「一個一定成立」配「一個一定不成立」
├── mutations.sh   把查詢腳本弄壞 N 種，看 verify.sh 會不會紅
└── sources/       外部來源的快照與原句對照表，不用相信轉述
```

`07-does-it-even-exist` 是這一型。它多一條規矩：
**「查不到」跟「沒問到」必須分開報。** 網路斷了、工具沒裝、代理擋掉，
在畫面上跟「註冊處說沒有這個名字」長得一模一樣，而兩者的結論相反。
所以每一輪開頭先問一個一定在的和一個一定不在的，兩邊都答對後面才算數；
問不到的時候離開碼是 2，不是 0 也不是「沒有」。
