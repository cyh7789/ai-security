# 02 祕密掃描的六個假通過

對應 [Day 2](https://ithelp.ithome.com.tw/articles/10401002)。

```bash
bash verify.sh        # 跑全部六個
bash verify.sh 3      # 只跑第 3 個
```

整支跑在 `mktemp -d` 開的暫存目錄裡，不碰你的任何檔案，跑完自動刪掉。
需要 `git` 與 `curl`，不需要安裝任何東西。

## 這份跟其他 recipe 不一樣的地方

其他 recipe 是「`before/` 有洞，修完 `verify.sh` 變成通過」。

這一份沒有 `before/`，因為 Day 2 要修的不是程式碼，是**檢查方法**。
所以 before 與 after 都在同一支腳本裡：每個情境跑兩種寫法，
`naive` 是直覺的那種，`fixed` 是知道坑在哪之後的那種。

每個情境裡 `naive` 都會給你一個看起來沒事的結果，而東西其實在那裡。

## 六個情境

| # | 情境 | naive 會告訴你 | 實際上 |
|---|---|---|---|
| 1 | 檔案早就被 track 了 | `git status` 乾乾淨淨 | 還在索引裡，`.gitignore` 對它無效 |
| 2 | `check-ignore` 有輸出 | 看到規則了，應該有擋 | 那是 `!` 開頭的放行規則，一樣 exit 0 |
| 3 | 查歷史的 pathspec | `'*.env*'` 查完是乾淨的 | `config/secrets.json` 它一個都不認 |
| 4 | 合併簡化 | `--all` 已經很完整了 | 合併結果跟主線相同的那一側被整段跳過 |
| 5 | 用 `sed` 遮掉值 | 值都被換成 `<值略>` 了 | 路徑含冒號的那行原樣印出明文 |
| 6 | 搜 `sk-` 驗有沒有漏出去 | 數字是 0，沒漏 | 服務沒通是 0、殘留檔會騙你、關鍵字會假陽性 |

## 為什麼值得跑一次

這六個沒有一個會噴錯誤訊息。它們的失敗方式都是**安靜地給你一個通過**，
而你會因此停止動作。這比報錯危險，報錯至少你知道要處理。

第 5 個是這裡面最貴的：`sed` 對不上樣式的行是**原樣輸出**的，
所以那條「保護你的」指令在特定路徑下會把明文金鑰印到螢幕上，還不報錯。

## 這支腳本自己也踩過一次

第 6 個情境的第三段（殘留檔）是寫這份 recipe 時撞出來的。
同一支腳本第一次過、第二次沒過，因為 `curl` 連不上時不會覆蓋 `-o` 指定的檔案，
`grep` 讀到的是上一次的內容。

驗證腳本自己也會有假通過。所以每一支寫完都要連跑兩次。
