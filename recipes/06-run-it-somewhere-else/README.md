# 06 它在哪裡跑

對應 [Day 6](https://ithelp.ithome.com.tw/users/20138924/ironman/9086)。

```bash
bash verify.sh        # 全部
bash verify.sh 1      # 只跑本機那節（不需要 docker）
bash verify.sh 4      # 只跑「多一個 -v 就破功」那節
bash mutations.sh     # 反過來：把隔離弄壞，看上面那支會不會抓到
```

**跑之前先讀 `suspect.sh` 跟 `verify.sh`。** 這個 recipe 講的就是不要跑你沒讀過的東西，
兩支加起來三百多行，`suspect.sh` 只有三十行，五分鐘讀得完。
第 4 節會把你的家目錄**唯讀**掛進一個沒有網路的容器一次，那正是它要示範的事。

需要 `bash`、`curl`，後三節需要 `docker`（`podman`、`nerdctl` 也認，但**只在 Docker 上實測過**。
`flags.sh` 那份掛載白名單是照 Docker 量的，podman 會多 bind 一個 `/run/.containerenv`，
真的遇到就把它加進白名單，那不是隔離破了）。
沒有容器 CLI 的時候後三節會跳過，而**跳過會讓離開碼變成 1**。
`bash verify.sh && echo 通過` 不該在一台完全沒有容器隔離的機器上印出那句話。
另外「沒裝」跟「裝了但引擎沒回應」分開報：後者是紅燈不是跳過，因為那不是這台機器不適用，是你要驗的東西壞了。

## 這裡面有什麼

| 檔案 | 是什麼 |
|---|---|
| `suspect.sh` | 假裝是 AI 給你的「跑這個就把殘留金鑰掃出來」腳本 |
| `Dockerfile` | 關它的地方。裡面什麼都不留 |
| `flags.sh` | **唯一一份旗標清單**，加上「容器裡只准看到哪幾個掛載點」的白名單 |
| `run-isolated.sh` | 預設全關的 `docker run`，`source flags.sh` |
| `verify.sh` | 四節：本機／容器／唯讀與權限／多一個 `-v` 就破功，也 `source flags.sh` |
| `mutations.sh` | **故意把隔離弄壞十三種，看 `verify.sh` 會不會紅。** 有一種沒紅就是假綠燈 |
| `PROMPTS.md` | 文章裡那組「同一個模型問兩次」的原始提示、回答節錄、工具版本 |
| `sources/` | 每個旗標的官方原句快照與對照表，不用相信轉述 |

**它會動到你機器上的兩樣東西**：第 4 節會把你的家目錄**唯讀**掛進容器一次
（那正是它要示範的事），跑完之後留下一個約 14 MB 的映像檔。要清掉：

```bash
docker rmi ai-security-day06-verify ai-security-day06
```

`suspect.sh` 前半段做的正是它宣稱的事，後半段只問「這幾個路徑讀不讀得到」，
**不開檔、不輸出內容、不送任何東西出去**。真的要偷的腳本不會印給你看。

## 每一條「找不到」前面都要有一條「找得到」

這一節的檢查形狀全是「某個東西不見了」：讀不到那些檔案、連不出去、寫不進去。
問題是**腳本沒跑起來、掛載沒生效、容器裡沒有 curl，症狀長得一模一樣**。

所以每一條都配一個正向對照：

| 「找不到」那條 | 撐它的「找得到」 |
|---|---|
| 容器裡讀不到家目錄的檔案 | 本機讀得到（第 1 節）＋ 腳本在容器裡真的跑完了 |
| `--network none` 連不出去 | 同一個容器不加那個旗標就連得到 |
| 唯讀擋掉寫入 | `/tmp` 寫得進去，而且掛載真的在 |
| 沒有多開別的掛載 | 直接列出容器裡的掛載點，跟 `flags.sh` 的白名單逐項比 |
| 掛了家目錄就讀得到（第 4 節） | 沒掛的時候讀不到（第 2 節） |

少了右欄，好幾種「其實沒有隔離」的配置都會跑出滿分綠燈。這不是假設，全部實測過。

還有兩條規矩是被打回來才補上的：

- **那個「找得到」不能由被測的東西自己提供。** 原本的判準是「`suspect.sh` 的輸出裡有沒有那行標題」，可是它正是你還沒讀完的那支，印完 `exit 0` 就騙過去了。現在探針另外跑一發，那一發不執行 `suspect.sh`
- **旗標只准有一份。** 原本 `verify.sh` 自己抄了一份，把 `run-isolated.sh` 的旗標刪光它照樣滿分，於是「驗證過生效」講的不是讀者手上那一份。現在兩邊都 `source flags.sh`

## 為什麼要有第 1 節

第 2 節的結論是「容器裡這幾條都讀不到」。這句話在**沒有隔離的時候也可能成立**，
只要那幾個檔案本來就不存在。所以第 1 節先在本機跑一次同一支腳本，
本機一條都讀不到就直接報紅，因為那代表這台機器上這組比較沒有鑑別力。

同一個道理用在網路上：第 2 節說「連不出去」，前提是第 1 節證明過本機連得出去。

## 第 4 節是這個 recipe 的重點

第 4 節跟第 2 節只差一個 `-v`：家目錄掛在 `/host`。
網路一樣關著、唯讀一樣開著、一樣不是 root 在跑，然後容器讀得到的東西跟本機一模一樣。

**「有沒有放進容器」不是判準，「掛了什麼、開了哪條線」才是。**

## 一個實測到的細節，以及它的邊界

macOS、OrbStack、Docker 28.5.2，2026-08-06 實測：**容器裡 `--user 0` 跟
`--user 10001` 讀同一個唯讀掛載，結果一模一樣。**

不要讀成通則。原生 Linux 的 bind mount 保留檔案原本的 uid 與權限位，root 有
DAC override 而一般 uid 沒有，結論可能相反；macOS 是先過一層虛擬機的檔案分享。
`USER runner` 那行還是要留，只是在這個組合下它擋的不是讀。

（這裡原本還寫了第二條「同一個絕對路徑掛載會靜默消失」。那條是錯的，
原因是作者的量測環境改寫了 `-v` 的參數，`docker inspect` 一看就穿幫。
已刪除。）

## 邊界

這裡管的是「執行的時候把它關在哪裡」。
「裝進來之前信不信它」是另一件事，Day 7 那天處理。

容器擋得住的是**你本機這一次執行**。同一個惡意套件進了 CI 和正式環境照樣跑，
那裡沒有人幫你加 `--network none`。

## 第 3 節為什麼看 `CapBnd` 不看 `CapEff`

容器裡跑的是非 root（`USER runner`），這種情況下 `CapEff` **一律全 0**，
不管你有沒有下 `--cap-drop ALL`，連 `--privileged` 都還是 0。
拿它當判準等於沒判。實測（macOS、Docker 28.5.2、2026-08-06，同一個映像檔）：

| 旗標 | `CapBnd` |
|---|---|
| 什麼都不加 | `00000000a80425fb` |
| `--cap-drop ALL` | `0000000000000000` |
| `--privileged` | `000001ffffffffff` |

分得出來的是 bounding set。
