# 16　誰在檢查這張單是不是你的

搭配 Day 16。前一份是 [15-tools-not-a-master-key](../15-tools-not-a-master-key)。

兩件事：一台把訂單編號當唯一查詢條件的 server，還有一個問題的答案。

**那個問題：「AI 生的 CRUD 幾乎必然只做驗證、跳過授權」，現在還成立嗎。**

## 先跑起來

沒有相依套件，有 Node 就能跑。

```bash
bash verify.sh              # 20 條檢查，一發真模型都不打
bash probe.sh before        # 把編號從 1001 數到 1008
bash probe.sh after         # 同一輪，修過的版本
bash calibrate.sh           # 偵測規則的 M 要填多少
```

`probe.sh` 的判定看回傳的內容，不看狀態碼。狀態碼會騙人：500 也可能夾帶完整訂單。

```
before：越權拿到 6 張別人的訂單
after ：越權拿到 0 張別人的訂單
```

## 這裡面有什麼

| 檔案 | 做什麼 |
|---|---|
| `before/server.mjs` | 查詢條件只有訂單編號。錯誤訊息把資料表名稱跟檔案行號印出去 |
| `after/server.mjs` | 跟上面只差兩處，都標了註解 |
| `probe.sh` | 對其中一台打正常流量與越權流量，印表，順手留存取紀錄 |
| `access-log.mjs` | 存取紀錄。最重要的是 `owner` 欄：被碰到的資源屬於誰 |
| `detect.mjs` | 偵測規則：同一個 session 在 N 秒內碰了 M 個別人的資源 |
| `calibrate.sh` | M 填多少不是猜的，是拿自己的正常紀錄掃出來的 |
| `prompts/` | 八份需求，彼此的差別可以逐行 diff |
| `judge.mjs` | 判一份生成的處理函式有沒有綁身分。判行為，不讀程式碼 |
| `run-gen.sh` | 兩組隨機交錯生成，逐份判決 |

## 量出來的：96 發，沒有一發外洩

`runs/2026-08-15/` 是完整紀錄，96 份生成的程式碼加 96 份模型回覆原文。重算：

```bash
node summarise.mjs runs/2026-08-15/results.tsv
```

| 組 | 需求換掉的那件事 | 綁了身分 |
|---|---|---:|
| `bare` | 素需求（動筆前鎖定的對照組） | 12/12 |
| `owned` | 多一句「這是使用者的私人資料」（實驗組） | 12/12 |
| `vague` | 多一句「請注意安全性」 | 12/12 |
| `nohint` | `req.user.id` 混在 traceId、locale 中間 | 12/12 |
| `nested` | 擁有者隔一層，請款單身上沒有 `ownerId` | 12/12 |
| `list` | 擁有者由網址參數帶進來 | 12/12 |
| `patch` | 給一份沒綁身分的現成程式碼，只要求加功能 | 12/12 |
| `patch-asked` | 同上，多一句「順手看有沒有安全問題」 | 12/12 |

主比較是動筆前鎖定的 `bare` 對 `owned`，12/12 對 12/12，p=1.0000。
其餘六組是看到「兩組都綁」之後才加的探索組，**跑過的組全部列在這裡，沒有挑**。

`patch` 那組最意外：需求只叫它加 `?fields=` 參數，它連我埋在裡面那個沒有身分核對的洞
一起補了，12 份都補。

## 分岔的是另一欄

擋下來的時候回什麼碼，同一顆模型給了兩種答案：

| 組 | 403 | 404 |
|---|---:|---:|
| `list` | 12 | 0 |
| `bare` | 1 | 11 |
| `nested` | 1 | 11 |
| 其餘五組 | 0 | 12 |

**403 等於承認那筆資料存在。** 查單筆的端點回 404，查清單的回 403，
拿這兩種回應交叉問一輪就把有效編號列舉出來了。這一欄比「有沒有擋住」更會分岔。

## 偵測規則：M 是量出來的

```bash
node detect.mjs logs/after-scan.tsv --window 60 --owners 3
# logs/after-scan.tsv：s-scan 命中，0.1 秒內碰了 5 個人的資源（擁有者 2、3、4、5、6，共 6 次，回應 404）
```

`calibrate.sh` 把 M 從 1 掃到 6，找「正常紀錄零誤報、掃描紀錄還抓得到」的最小值。
這份示範算出來是 **M=3、視窗 60 秒**：正常流量裡有一個客服 session 會碰到兩個客戶，
所以 1 跟 2 會誤報；6 抓不到，因為那次掃描只碰了 5 個人。

**換一個系統就要重算。** M 量的是你的正常流量裡一個 session 合理會碰到幾個別人的資源。
抄來的門檻只會讓你整天收到通知，然後把規則關掉。

修好之後這條規則還是有用：`after` 那組擋下來的是 404，紀錄裡照樣看得到
同一個 session 在數別人的編號。前提是 `owner` 那一欄要記，
而回應不講是誰的、紀錄要講，這兩件事不衝突。

## 換成你自己那套

1. **`probe.sh`**：換成你自己的端點清單與兩個測試帳號。這一步不能靠讀程式碼代替
2. **`detect.mjs`**：`owner` 那一欄要接得到你的資源擁有者。接不到就先去補存取紀錄
3. **`prompts/`**：想量你自己那顆模型的話，八份需求照抄，換掉資料層那幾行

## 已知的邊界

- **這是一顆模型、一天、每組 12 發。** 換一顆模型或換一種框架就是另一回事。
  96 發全綁只證明「必然不綁」這句話對這顆模型是錯的，不證明「它永遠會綁」
- **需求裡都寫了 `req.user.id` 拿得到。** `nohint` 那組是為了這個做的：
  把它混進 traceId 跟 locale 中間，結果一樣。但完全不提身分的需求沒有量，
  因為那樣它連綁的材料都沒有
- **判準只問「別人的資料有沒有回來」。** 一份會回 500 但把資料寫進 log 的程式碼，
  這裡會被判成擋住了
- **DNS、快取、反向代理都不在這份裡。** 這份只看應用層那一個判斷
