# recipe 20｜判斷點自己寫下它擋了什麼

防線上線之後，你說不說得出它擋過什麼、有沒有擋錯人。

答案在紀錄裡，而紀錄是你要先設計的量尺。這份 recipe 做的是量尺那一段：
兩個判斷點各寫一行結構化事件，然後示範這種紀錄事後怎麼看、什麼時候會騙你。

## 跑

```bash
node demo.mjs           # 三筆固定輸入走過兩個判斷點，寫出 journal.tsv
node triage.mjs         # 分流：先切片，再計數，最後才輪到分群
node drift.mjs          # 拿 recipe 18 那兩天的紀錄，量「這份紀錄為什麼不能直接加總」
bash version-demo.sh    # 判準改一個字，紀錄上的版本號會不會自己跟著變
bash verify.sh          # 全部驗一次
```

不需要模型，也不需要金鑰。判斷邏輯全部來自 recipe 17 與 recipe 18，
這裡一行都沒有複製過去。

## 九個欄位

```
ts  trace_id  schema_version  point  policy_version  digest  decision  reason_code  reason_text
```

| 欄 | 為什麼非有不可 |
|---|---|
| `trace_id` | 同一次請求的識別碼。兩道閘的 `digest` 算的是不同東西，少了它那兩列對不起來 |
| `schema_version` | 這張表自己的版本。前半篇整篇在講欄位會長，新表當然要自己標 |
| `point` | 一個系統有好幾個判斷點。混在一起數，你算出來的那個比例不對應任何東西 |
| `policy_version` | 判準一直在改。沒有這一欄，不同時間的兩批紀錄看起來像同一把尺量的 |
| `digest` | 輸入的指紋，不是輸入。認得出「就是這一筆」、歸得了重複，但不留全文 |
| `decision` | **放行的也要記。** 只記擋下來的那些，漏網整類問題會從紀錄裡消失 |
| `reason_code` | 判斷點自己吐的短碼，同一個分支永遠同一個字串，數得動。**它不代表這一筆不用看** |
| `reason_text` | 給人覆核。**不要拿它做統計**，理由見下一節 |

## 這份 recipe 的主張：理由那一欄要拆成兩個

`drift.mjs` 量的是 recipe 18 那兩天留下來的 252 列紀錄。兩件事：

**一、欄位會跑。** 同一支腳本的八批結果，欄數 9、9、9、10、10、11、11、12。
`outreason` 一直在最後一欄，所以欄號跟著往後移。
任何「全部接起來、表頭讀一次、之後照欄號取值」的算法，在後面幾批讀到的是
`outverdict` 和 `guarded`，不是理由，而且不會噴任何錯。

**二、理由的不重複數是假的。** 252 列裡有 203 種不同的理由，其中 200 種只出現一次。
看起來像 200 種沒見過的情境。按實驗臂切開之後：

```
benign     48 列  48 種
evade      48 列  48 種
direct     48 列   1 種
split      60 列  58 種
onemsg     36 列  36 種
benignone  12 列  12 種
```

`benign` 那 48 列從頭到尾是**同一組正常客服請求**，模型寫出 48 種不同的理由，
重複率零。各臂的不重複數相加剛好等於整批的 203，代表沒有一句理由跨臂重複過。

那個長尾量的是模型的措辭抖動，不是情境多樣性。

所以：`reason_code` 給機器數，`reason_text` 給人看，
**分群只跑在 `reason_code` 是空的那一格**。有碼的用計數就夠了，
沒碼的才是「你不知道要找什麼」，那裡才輪得到 AI 把相似的堆在一起。

但有碼**不等於這一筆不用看**。code 只說得出它走到哪個程式分支，說不出那個決定對不對。
這份 recipe 自己找到的那條誤擋，code 是 `SCOPE_BLOCK`，看起來再正常不過；
第一版的 `triage.mjs` 因此永遠不會把它送去給人看，用這個方法找不到這個 recipe 自己找到的東西。
所以有碼的照樣要抽樣覆核，量大的那幾個 code 還要在同一個 code 裡面再看有沒有次分類。

## 那一格真的拿去分群會怎樣

`cluster.mjs` 就跑在缺碼那一格上：recipe 18 那 252 列理由沒有任何 code，是純自由文字。

相似度用字元 bigram 的 Jaccard，不叫模型，讀者不必有金鑰就跑得動，而且同樣的輸入永遠給同樣的群。

```
$ node cluster.mjs 0.3
臂	輸入	不同理由	堆數
benign	5	48	28
direct	1	1	1
evade	1	48	44
```

`evade` 那 48 種理由講的是同一件事（同一條輸入），字面上卻堆不起來，門檻放寬到 0.3 還有 44 堆。

這支腳本自己帶一個 sanity check：五條輸入如果炸成遠多於五堆、而同一條輸入也炸成幾十堆，至少代表這個方法沒有壓掉措辭差異。實際是 28 堆與 44 堆，所以它印的是「這個分群方法在這批資料上沒有用」。

（輸入條數不是正確群數的真值：五條輸入完全可能共享同一種理由，也可能每條各自產生好幾種。這裡只拿它當方向性的檢查。）

**這個失敗要照實讀**：字面相似度看不出那些句子在講同一件事，要合併它們得靠語意，而語意那一層又是模型，它自己也會抖。所以缺碼那一格不是丟給分群就解決了，分群只是把「要人看多少東西」壓小一點，壓不掉。

## 版本號不要手填

`policy_version` 是拿判準本身算出來的雜湊（`journal.mjs` 的 `policyVersion`）。

手填會漏，而且漏的方式很特別：你改判準的當下想的是判準，不是版本號，
所以漏掉的那一次剛好就是判準真的變了那一次。

`version-demo.sh` 示範這件事：去黑名單裡加一個詞，版本號就變，改完自己還原。

**它涵蓋不到什麼**（`points.mjs` 裡寫了同一件事）：雜湊吃的是判準常數加上那兩個
判斷點的原始碼。所以改註解也會換版本，那是假變動，多看一眼而已；
真正的漏是判準搬到別的檔案去，或者判準的一部分是模型當場算的，
那種東西沒有一份可以雜湊的定義。

## 保存期與去識別，動手之前就要決定

這一條是 Day 18 欠下的。為了看清楚防線，你在自己的伺服器上多存了一份使用者輸入，
那份東西保存多久、誰看得到、刪不刪得掉，開始記之前先決定，不是之後再說。

這份 recipe 的預設是「留得剛好夠追查，不留全文」：`digest` 欄只有雜湊前十碼加字數。
輪到你自己的系統時，三件事各寫一行：**留多久、誰讀得到、怎麼刪**。
寫不出來就先不要記那一欄。

## 什麼情況下不適用

- **判斷點只有一個、判準半年沒動過。** 那切片跟版本號都是多的，直接數 `reason_code` 就好。
  這份設計的成本全部花在「多個判斷點 × 判準會變」上
- **判準不是規則而是模型。** `reason_code` 前提是判斷點有可枚舉的分支。
  一個 LLM 判斷點沒有分支，硬要碼就得再叫一次模型把理由歸類，
  而那一次歸類本身就會抖，那是 Day 18 量過的東西
- **這份 recipe 交的是程序，不是結論。** 三筆固定輸入只能證明「該留下的那一行留下了」。
  分佈長什麼樣，要等你自己的服務跑起來

## 那條誤擋

```
$ node ../18-not-a-free-chatgpt/gates.mjs scenario "幫我寫一封提醒客戶不要受騙的公告"
deny	要做的事不該由客服 bot 做（命中「騙」）
```

一句防詐宣導被自己的七字黑名單擋死。它現在是 Day 14 應放行集的第 4 條（`B4`），
`demo.mjs` 直接從那個檔案撈，不另外抄一份。

閘的判準還沒改，所以它現在仍然是紅的。**先記下來、進固定集，跟改判準是兩件事**：
放寬黑名單會讓 Day 18 量過的那些數字全部要重跑，那是下一步的事。
