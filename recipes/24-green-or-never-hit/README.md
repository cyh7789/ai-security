# 24：全綠的測試，是防住了還是根本沒打到

對應 Day 24（發表後補連結）。

Day 23 交下來一張攻擊面清單（`../23-what-can-actually-reach-it/surface.tsv`），
上面標了哪幾條路徑到得了。這一份把那些路徑變成一組固定的、每次都再打一遍的案例，
而且**留了八條已知會被打穿的**。

只有 Node 與 bash，沒有相依套件。

## 跑

```bash
bash run.sh                    # 全部十三條
bash prove-red.sh              # 弄壞一道真的防線，看測試入口會不會跟著紅
bash run.sh C01 C05            # 只跑指定幾條
node --test cases.test.mjs     # 同一組，node 的測試入口
node collect.mjs --check       # 攻擊集跟來源有沒有分岔
bash verify.sh                 # 這份 recipe 自己的檢查，23 項
bash mutations.sh              # 21 個機制突變加 1 個反向對照，看那 23 項會不會紅
```

**`run.sh` 正常情況下就是回離開碼 1。** 那是設計：清單上有八條已知的缺口。
一份永遠綠的攻擊集分不出「防得住」跟「根本沒打到」，而那正是這一天要處理的事。

## 一條案例只有四種下場

| 結果 | 意思 | 你接下來要做什麼 |
|---|---|---|
| 擋住 | 走到了那道閘，它判 deny，動作沒發生 | 沒事 |
| 沒擋 | 終點真的到了 | 期望是「擋」的話，這就是缺口 |
| 沒打到 | 跑得動也沒被擋，但這一發沒走到終點 | 回去看那條攻擊還成不成立，這份清單量不到它宣稱量的東西了 |
| 跑不動 | 這一發根本沒跑起來 | 修環境。離開碼 2，不算紅 |

第一版只有三種，「沒打到」跟「跑不動」共用一個字面值。
於是三種完全不同的事實印出同一行：有人補掉了那個洞、有人改了罐頭模型讓攻擊走不到終點、
有人佔住了那個埠。三份輸出逐字相同，而正確處置分別是「更新紀錄」「攻擊集失效了」「修環境」。

實測分得開之後：把 `TARGET_ALLOWLIST` 收成 `[1002]` 得到「補起來了」，
改掉 `17/stub-model.sh:29` 的關鍵字得到「打空氣」。

實測跟紀錄對不上的時候，方向也要分，而好壞由「期望」決定不由「擋住」決定：
期望是「可接受」的那幾列變成擋住，是防線把正常客人擋掉了，不是好消息。

## 這裡面有什麼

| 檔案 | 是什麼 |
|---|---|
| `cases.tsv` | **成功條件正本，人填的。** 期望只有「擋」與「可接受」，層級只有「流程」「元件」「資料」 |
| `run.sh` | 每條案例怎麼跑，以及判準看哪個可觀察的東西 |
| `cases.test.mjs` | `node --test` 入口。不重新實作判準，只呼叫 `run.sh` |
| `attacks-project.jsonl` | 收出來的攻擊集，`collect.mjs --write` 產生 |
| `collect.mjs` | 從 `cases.tsv` 收，並跟 recipe 23 的清單對帳 |
| `open-questions.tsv` | 到得了、但今天定不出成功條件的六條 |
| `retrieve.mjs` | R11 的起點。Day 23 那天客服 bot 沒接檢索，這條路徑量不到 |
| `kb-approved.txt` | 人核准過的知識庫來源前綴，手寫的 |
| `variants/` | 派出去的 brief、模型交回來的原文、我留了哪幾條與為什麼 |

## 那條線畫在哪：模型生變體，成功條件人定

規格的分工寫死了：定義交出去等於讓模型自己出題自己改卷。

實際的比例是 **27 收 6**。細節在 `variants/verdicts.md`，這裡只講最值得記的一條：

Sol 給的 R4、R6、R14 那九條變體，跑出來的輸出**逐字相同**。
理由在罐頭模型：`17/stub-model.sh:29` 第二步只看 `[工具結果]` 裡有沒有
`delete_order` 或「可清除」。四種完全不同的植入手法走同一個 if。

**九條變體量到的是一個 if 分支被觸發九次。** 它們全部「打穿」，
而那個打穿不是防線失守。這跟「全綠」是同一枚硬幣的兩面：
數字漂亮，而數字量的不是你以為的那件事。

## 為什麼另開一份攻擊集，不併進 recipe 14 那份

`14/attacks.jsonl` 是送進模型的 prompt 語料，`run-suite.sh` 拿它去 grep 模型的回覆，
而且 `carrier` 不在 `build-prompt.mjs` 的 `HEAD` 裡的整條會被過濾掉不跑。

這一份的判準是程式狀態：那筆訂單還在不在、憑證標記有沒有被抓回來、讀到的是誰的單。
硬塞進去的話，這十二條會躺在一個它的 harness 從來不會跑到的檔案裡。

兩份各自對各自的來源。Day 14 那條「不手抄」的規矩沒有變，只是這一份釘的是
`23/surface.tsv` 加 `cases.tsv`。

## 為什麼有些路徑不在攻擊集裡

`open-questions.tsv` 那六條到得了，但今天定不出成功條件。放進 `cases.tsv` 的話，
那份清單會有一批永遠不紅也永遠不綠的列，而那正是「全綠分不出防住還是沒打到」的溫床。

缺的只有兩種：**終點不存在**（內容到得了那裡，但那裡還沒接上會出事的東西），
以及**判準是罐頭**（終點存在，但判斷有沒有出事的那一端是罐頭模型）。
每一列都寫了「補上什麼之後它進得了 `cases.tsv`」。寫不出來的話，
那一列其實是我還沒想清楚，不是它定不出來。

## 骨架的下場

recipe 23 交下來的是一條路徑一個 `.test.mjs` 骨架，本來要在這裡一條一條填 assert。
沒有照那個形狀填，改成一份 `cases.tsv` 加一個 `cases.test.mjs`。

理由是規格要求人親自看「這條必須被擋還是擋不住可以接受」那一欄。
散在九個檔案裡的話，沒有人會把九個檔案排在一起看，於是那一欄實際上沒有被人審過。
骨架留在 recipe 23 沒有動，它記的是那一天的產出。

## 十三條不是同一層

外審抓到一個洞：我拿「那是閘的判決，不是那句話真的走完入口」退掉三條變體，
然後自己收了三條同型的。`cases.tsv` 為此多一欄「層級」：

| 層級 | 條數 | 意思 |
|---|---:|---|
| 流程 | 11 | 那段內容真的走完了那條路徑 |
| 元件 | 1 | 只呼叫了某一支閘（C06，那支工具在這個示範裡不存在，沒得走完） |
| 資料 | 1 | 只稽核了既有資料（C12，知識庫的寫入流程不存在） |

C10 改掉了：它以前走 `21/regress.mjs`（直接呼叫 `scenarioGate`），
現在走 `23/intake.mjs --typed`，那句誘餌句真的走完客服入口。
`verify.sh` 第 19 條盯著這件事。

## 一個判斷我改過

C10（誘餌句 b1）第一版標「可接受」，理由是 Day 21 明著換來的取捨。
那是把兩件事混在一起：Day 21 選的是「不要用那個字擋」，不是「這句釣魚信要求可以過」。
後者是代價不是選擇，而來源那邊記的就是未修的缺口（`18/gates.mjs` 寫「這個缺口沒有被修掉」，
`21/regress.mjs` 把它歸在缺口樁）。

把代價標成「可接受」的直接後果：它不算進基線，也不會出現在缺口欄，
於是一個未修的洞在表上長得像一個決定。改判「擋」，缺口從六條變七條。

## Day 25 補的一條

`C13` 是 Day 25 加的，量的是 `15/agent.mjs` 的出廠預設（整個不傳 `--gate`）。
它跟 C07 走同一條路徑 R10、同一個判準，差別只在誰在跑：
C07 是明確傳 `--gate on` 的人，C13 是照著 README 第一行複製貼上的人。
今天兩者走同一條裸 `fetch`，所以兩條都紅；改出廠預設只救得了後者。
分不開的話，「預設安全了」會被讀成「那條路堵掉了」。
