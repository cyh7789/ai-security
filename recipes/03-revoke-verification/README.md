# 03 處置外洩憑證時的三個假通過

對應 [Day 3](https://ithelp.ithome.com.tw/articles/10401276)。

```bash
bash verify.sh        # 跑全部三個
bash verify.sh 2      # 只跑第 2 個
```

整支跑在 `mktemp -d` 開的暫存目錄裡，不碰你的任何檔案，跑完自動刪掉。

情境 1 需要 `gitleaks`，系統沒裝會自己抓一份到暫存目錄，用完刪掉，不會裝進你的系統。
情境 2 要連外網打公開端點，用的是明顯無效的假金鑰，不會動到任何帳號。
兩者都取不到的時候會印 `沒有結論` 加原因，不會靜靜跳過。

## 跟 02 一樣，這份修的是檢查方法

沒有 `before/`。每個情境跑兩種寫法：`naive` 是直覺的那種，`fixed` 是知道坑在哪之後的那種。
三個情境有同一個形狀：**失敗的畫面跟成功的畫面幾乎一樣。**

## 1. hook 分不出「有祕密」與「掃描器自己壞掉」

常見的 pre-commit hook 長這樣：

```bash
gitleaks git --staged --redact -v || {
  echo "偵測到疑似祕密，commit 中止"
  exit 1
}
```

問題在 `||` 收下了所有非零離開碼。gitleaks 預設用 `1` 表示「找到祕密」，
但它自己跑不起來的時候回的也是 `1`：

```
                        乾淨   有祕密   設定檔壞掉
naive（預設）             0       1          1
fixed（--exit-code 2）    0       2          1
```

所以設定檔哪天壞掉，你每次 commit 都會看到「偵測到疑似祕密」。
腳本會實際裝兩種 hook，對一個**完全乾淨**的 commit 各跑一次給你看：

- naive 說「偵測到疑似祕密，commit 中止」，而那個 commit 裡什麼都沒有
- fixed 說「gitleaks 沒跑完，這次等於沒掃」

差別不只是訊息好看。看到前者你會去翻檔案找不存在的祕密，找不到就開始懷疑工具、
最後習慣性繞過它；看到後者你知道要去修設定檔。

修法是讓「找到祕密」用一個不會跟錯誤撞號的離開碼：

```bash
gitleaks git --staged --redact -v --exit-code 2
case $? in
  0) ;;
  2) echo "偵測到疑似祕密，commit 中止"; exit 1 ;;
  *) echo "gitleaks 沒跑完，這次等於沒掃，commit 中止"; exit 1 ;;
esac
```

**什麼情況不適用**：`--exit-code` 是 gitleaks 的參數，其他掃描器要查自己的文件。
真正可移植的是那個判準：任何「非零就當成有問題」的檢查，都要先確認工具用不用
離開碼區分「找到東西」與「我壞了」。

## 2. 撤銷驗證：只換網址，標頭沒換

撤銷金鑰之後拿舊鑰打一發 API 確認它死了，這步是對的。但範例通常長這樣：

```bash
curl -sS https://api.provider.example/v1/models \
  -H "Authorization: Bearer $OLD_KEY"
```

`Authorization: Bearer` 是其中一家的格式。換一家可能要 `x-api-key`，
可能還要版本標頭。**只換網址、留著原本的標頭，你會拿到一個看起來像撤銷成功的錯誤。**

腳本打同一個端點兩次給你看：

| | 回應 |
|---|---|
| naive：標頭錯（Bearer） | `"type":"authentication_error"`，`Invalid bearer token` |
| fixed：標頭對、金鑰無效 | `"type":"authentication_error"`，`invalid x-api-key` |

**`type` 完全一樣**，只有 `message` 分得出來。如果你的驗證只看狀態碼或只看 `type`，
一把還活著的金鑰會被你判成已撤銷。

腳本還會打一個不存在的端點，回 404。這是同一件事的第三種版本：
你要挑一個**撤銷前用同一把鑰匙打得通**的端點，否則拒絕跟撤銷無關。

**什麼情況不適用**：這裡示範的兩種格式與訊息字串會隨供應商改版。
可移植的是做法：讀完整個回應，找到明確說「憑證無效」的那一段，而不是看某一個欄位。

## 3. `curl -s` 把連線錯誤吞掉

```
naive  curl -s   輸出：「」            離開碼 6
fixed  curl -sS  輸出：「curl: (6) Could not resolve host: ...」  離開碼 6
```

`-s` 連錯誤訊息一起關掉。網址打錯、DNS 掛掉、沒網路，畫面上什麼都不會出現，
而你正在做的事情是「確認一把金鑰已經失效」。什麼都沒發生跟被拒絕，在這個情境下
是完全相反的結論。

用 `-o /dev/null -w '%{http_code}'` 只取狀態碼的話，拿到的是 `000`。
它不是 401，也不是任何形式的「被拒絕」，別把它讀成撤銷成功。

修法是 `-sS`：安靜但保留錯誤。

## 共同的判準

三個情境都是同一句話：**你的檢查要能分辨「通過」與「沒跑到」。**
分不出來的檢查比沒有檢查更糟，因為它會給你一個你會相信的答案。
