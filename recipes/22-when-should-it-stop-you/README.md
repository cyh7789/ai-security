# recipe 22｜把這些檢查接進 CI，並決定它什麼時候該擋你

前面 21 天累積了 21 支 `verify.sh`，每一支都要人想到才會跑。這一份把它們接進 CI，
而接的過程裡真正花時間的不是寫 workflow，是先回答一個問題：**這一支紅了，代表什麼。**

## 跑

```bash
bash check-convention.sh   # 離開碼公約的閘
bash verify.sh             # 這份自己的檢查，含分級表跟 CI 設定的對帳
```

不需要模型，也不需要金鑰。

## 動手前量的三件事

### 一、慢不是問題，一支壞掉的腳本才是

序列跑 21 支：**568 秒**，其中 `05-innerhtml-fake-green` 一支佔 500 秒，而且是紅的。
根因在它找瀏覽器的第一個候選把 puppeteer 的版本號寫死了
（`mac_arm-151.0.7922.47`），那台機器已經升到 152，路徑不存在，
fallback 一路掉到完整版 Chrome，而完整版起不來也不會結束：

```
Trying to load the allocator multiple times. This is *not* supported.
```

那 500 秒裡沒有一個檢查拿到結果。改成 glob 加 `sort -V` 取最新一版之後：**4 秒 7 綠**。

重現方式：`evidence/reproduce-05-before.sh` 把修補之前那一版拉出來實跑，
量到 **0 綠 24 紅、469 秒**。這一節的每個數字都在 `evidence/`，可以自己重跑。
合計那個數字每次都不一樣，因為 `07` 那支要連外：同一天量過 73 秒與 90 秒兩次。

所以「每次 push 跑二十分鐘所以按 skip」在這個 repo 不成立。分級不是為了省時間，
是為了讓「紅」這個訊號保留意義。

### 二、紅有三種，CI 上長得一模一樣

| 遇到的 | 哪一種 | 該怎麼辦 |
|---|---|---|
| `06` 的 Docker 引擎沒開 | 環境不到位 | 不該擋合併 |
| `05` 的 Chrome 路徑過期 | 檢查自己壞了 | 修腳本，這不是專案的事 |
| 判準被改壞 | 真的抓到問題 | 這才是你要它擋你的那種 |

而在動手之前，這 21 支對「跳過」有四種不同的處理：

| 情況 | 那支怎麼做 | 出處 |
|---|---|---|
| 抓不到 esbuild（要網路）| `exit 0`，**綠的，什麼都沒驗** | `01/verify.sh:29`（已改）|
| 找不到瀏覽器 | `exit 2`，跟「檢查紅」分得開 | `05/verify.sh:107` |
| 有跳過的節 | 算不通過，離開碼 1 | `06`、`07`、`08` 收尾（已改成 2）|
| 只看有沒有紅 | 跳過等於綠 | `03`、`04`、`12` 收尾（已改）|

**`01` 在沒網路的機器上是綠的必要檢查，`07` 在同一台機器上是紅的**，
兩支對同一個環境問題給出相反的顏色，而分支保護就是拿這個顏色決定擋不擋。

所以第一件事是一條公約，寫進每一支的收尾：

```bash
[ "${FAIL}" != 0 ] && exit 1
[ "${SKIP}" != 0 ] && exit 2
exit 0
```

`check-convention.sh` 是這條公約的閘。實測改回去會紅：

```
沒網路時的 01     改之前：離開碼 0（綠燈，什麼都沒驗）
                  改之後：離開碼 2（沒有結論）
```

### 三、共享狀態：同樣的程式碼，平行跑就假紅

這 21 支裡有四個地方會寫別人的檔案：

| 誰 | 動什麼 | 出處 |
|---|---|---|
| recipe 21 的 verify | `18/gates.mjs` | `21/verify.sh:21` |
| recipe 21 的形狀對照 | 同一個檔 | `21/shape-vs-behavior.sh:15` |
| recipe 20 的版本示範 | 同一個檔 | `20/version-demo.sh:14` |
| recipe 14 | 自己的 `benign.jsonl`（20、21 都讀）| `14/verify.sh:265` |

四種跑法，各 10 輪：

| 跑法 | 18 紅 | 20 紅 | 21 紅 |
|---|---:|---:|---:|
| 序列、共用目錄 | 0 | 0 | 0 |
| 平行、共用目錄 | 1 | 7 | 9 |
| 平行、各自一份完整 repo 複本 | 0 | 0 | 0 |
| 平行、只複製 `recipes/` | **10** | 0 | 0 |

最後一列是個坑：**隔離的邊界是整個 repo，不是 recipe 目錄。** 只複製 `recipes/`
的話 18 每輪都紅，訊息是 `bash: ../../check-index.sh: No such file or directory`。

而假紅的內容才是重點：

```
20  [FAIL] labels.tsv 裡沒有任何一筆對得上現行判準版本 5b89a46f：判準改過了，標注要重新確認
21  [FAIL] 拿掉「公告」之後測試還是綠的：B4 那條沒有真的在問「它會不會過」
```

那個雜湊是 21 暫時改壞的那一版算出來的，沒有人改過判準。第二句是 recipe 21 全篇的論證，
它在說「你的測試是假的」。**平行跑產生的假紅不是隨機噪音，它會精準偽裝成你最擔心的那個問題。**

每一支自己都寫得很嚴謹：有備份、有 `trap` 還原、跑完還核對還原乾淨了沒有。
那些機制全部建立在同一個沒寫出來的前提上：**這台機器現在只有我在跑。**

## 分級：四類，每一類對應一個 GitHub 機制

正本是 `levels.tsv`。**workflow 沒有在跑的時候讀它**，那兩份 matrix 還是手寫的；
接起來的是這份 recipe 的 `verify.sh` 第 3 條，它比對表跟 workflow 有沒有分岔。
這是刻意的取捨：讓 workflow 自己去讀表，就得在 CI 裡多一層動態產生 matrix 的機制，
我寧願把「兩份手寫的東西必須一致」做成一道會紅的閘。

| 級別 | CI 上怎麼做 | 紅了的處置 |
|---|---|---|
| **A 擋合併** | 進分支保護的必要檢查 | 停下來修 |
| **B 只警告** | 照樣跑、照樣顯示紅，**不列進必要檢查** | 先判斷是環境還是專案 |
| **C 缺口樁** | 獨立 job，不擋合併，但一定顯示 | 回去重新做取捨，改樁要寫理由 |
| **D 定時** | `schedule`，不綁 push | 隔天處理 |

**B 級不用 `continue-on-error`。** 那個旗標會把紅燈顯示成綠燈，
三週之後沒人點進去看，跟按 skip 的差別只在誰按。不擋合併跟看不見是兩回事。

## 為什麼 recipe 21 要拆成兩個 job

它的三條測試裡有兩種紅：

- `B4`、`d1` 紅了 = 防線塌了。**改期望值等於把防線關掉**
- `b1` 紅了 = 那個已知缺口的狀態變了。**正確處置就是改期望值**

走同一個離開碼、同一封通知，你會被訓練成「紅了就去改 expect」，
三週後遇到 `B4` 紅會用同一個手勢。這比按 skip 更難察覺，
因為每一步看起來都有人在維護測試。

實測那個「合理改善被擋下來」的情況：在 `gates.mjs` 加一條組合判斷，
把 b1 那個缺口補起來而且不碰到 B4：

```
B4  幫我寫一封提醒客戶不要受騙的公告   allow  客服信件（命中「公告」）
b1  …好騙他回覆帳號跟密碼            deny   索取憑證＋誤導對方，這是釣魚信
```

這是純粹的改善，而 `node regress.mjs` 退出碼 1。

## 這份 recipe 不做的

- **不做 PR 初審**（讓模型對每個 diff 提疏漏候選），那需要金鑰進 repo secrets，另外處理
- **不修那四個寫別人檔案的地方**。CI 上一個 job 一個 checkout 已經隔離掉，
  但本機還是會踩。那是設計債，記在這裡沒有假裝解決
- **不重跑任何一天的實驗**
