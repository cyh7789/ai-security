# 04 貼給 AI 之前的紅線檢查

對應 [Day 4](https://ithelp.ithome.com.tw/users/20138924/ironman/9086)。

```bash
bash verify.sh        # 跑全部七節
bash verify.sh 4      # 只跑第 4 節
```

全部在 `mktemp -d` 裡進行，不碰你的任何檔案，跑完自動清掉。需要 `bash` 與 `realpath`。

## 這支腳本在做什麼

Day 4 的產出是一份 `AI-SHARING.md`，寫下這個專案裡什麼算敏感。那份清單的第一段是檔名，
檔名可以翻成程式：

```bash
bash check-before-paste.sh .env          # 踩到紅線：.env
bash check-before-paste.sh src/format.js # 不在紅線清單上：src/format.js
```

**兩個都要跑。** 只跑會過的那個，你驗到的是「腳本會印字」，不是「腳本擋得住東西」。

它不是攔截器，沒有人會在每次 Cmd+V 之前跑它。它的用途是**檢查你的清單夠不夠具體**：
寫得出來，代表那幾條指得出實際的檔案；寫不出來，代表清單上還有「注意」「小心」這種
不能執行的條目。

## 離開碼分三種，因為「沒檢查成功」不是「乾淨」

| 碼 | 意思 |
|---|---|
| 0 | 不在紅線上 |
| 1 | 踩到紅線 |
| 2 | 這次沒有檢查成功，不要當成安全 |

會回 2 的有五種，訊息各自分開：沒帶參數、路徑不存在、參數是目錄、
symlink 失效、`realpath` 不在或解不開。

分開是有理由的。「這條 symlink 壞了」跟「你打錯字」要做的事完全不同，
而把兩者混成同一句話，你會拿錯的方向去查。同理，如果這五種都回 0，
那腳本每次出事都會告訴你「乾淨」，那比沒有腳本更糟。

## 三個設計決定，都是踩過才知道的

### `.env*` 不是 `.env.*`

少一個字，`.envrc` 就漏掉了。direnv 的設定檔裡常常有東西。

### 要解真實路徑

一個 `src/link.json` 指向 `../fixtures/real.json` 的 symlink，字串比對只看到 `src/`，
直接放行。加上 `realpath` 之後才擋得住。

### 檔名規則與目錄規則要分成兩個 `case`

想併成一個很自然，但併了就壞，而且壞得很安靜：
`basename fixtures/real.json` 的結果是 `real.json`，永遠對不上 `fixtures/*`。
不報錯、不警告，那條規則從此不成立。

`verify.sh` 第 7 節把這三個決定各拿掉一次，確認對應的檢查真的會轉紅。
突變的做法是**準備完整的替代腳本**，不是用 `sed` 改原始碼的文字，
因為後者綁死在寫法上，重構一次整組假性紅燈。

## 它擋不住什麼

這兩條是邊界不是 bug，`verify.sh` 第 6 節會實際跑給你看：

**寫死在檔案裡的內容。** 一個放在 `src/utils.js` 的金鑰它會放行，因為清單管的是檔案，
不是內容。那種東西歸 pre-commit 掃描（見 [recipe 03](../03-revoke-verification/)）。

**hard link。** `realpath` 只解 symlink，同一個 inode 的另一個名字它看不出來。
要擋得掃過整個紅線目錄比對 inode，成本不成比例，這支沒有做。

## 什麼情況不適用

清單裡的四條路徑（`.env*`、`docker-compose.yml`、`config/secrets.*`、`fixtures/`）
是範例，換一個專案就要換。這支腳本的價值不在那四條，在於它證明你的清單具體到可以被
機器執行。

還有一件更重要的：**這支腳本只涵蓋「你手動貼上」那條路。** 編輯器自動帶的 context
與 agent 主動讀的檔案都不經過它，那兩條要靠工具的忽略設定與 agent 權限，
不是靠這裡。
