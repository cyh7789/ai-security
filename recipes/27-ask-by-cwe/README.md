# 27：給它一個編號，要它挑檔案

對應 Day 27（發表後補連結）。

Day 26 那一份是逐檔問「這個檔有什麼問題」，錯得很難看。這一份換一種問法：
給它一個 CWE 編號跟整份程式碼，要它回答**哪幾個檔要看**。這才是它練過的那件事。

環境跟 Day 26 同一套（Apple Silicon、`mlx-lm`、同一份 q4 權重），
取得方式見 [recipe 26](../26-what-low-looks-like/)。

## 跑

```bash
export ANTARES_MLX=./antares-1b-mlx          # 或你自己放的地方

python3 hunt.py "$ANTARES_MLX"               # 十三個類別各問一次，原始輸出存進 hunt/
python3 hunt.py "$ANTARES_MLX" --rename      # 對照組：檔名換掉再問一次
python3 names-only.py "$ANTARES_MLX"          # 對照組：只給檔名不給內容
bash confirm.sh                              # 對它指出來的那個檔，真的打一次
bash verify.sh                               # 十五條檢查
bash mutations.sh                            # 突變測試，每一個都指名哪幾條該沒過
```

離開碼照 Day 22 那份公約：0 全部通過、1 有沒過的、2 環境不到位或有節被跳過，沒有結論。

第 10 條要重跑一整輪（約 73 秒）。`SKIP_RERUN=1 bash verify.sh` 可以跳過它，
但**跳過不是通過**：那一趟的離開碼是 2。

## 為什麼要問七個「這個專案沒有的類別」

因為只問埋過的那六類，量到的是「它找不找得到」，量不到「指定類別不存在時會怎麼答」。
論文的 Phase A 每一題都保證有洞；Phase B 會拿修補過的程式碼問同一個洞還在不在，
但論文沒有公布這一階段的結果。

所以這一輪的十三個問題分成兩半：六個有答案的，七個答案是「沒有」的。
後七題不是原始 Phase B，而是針對相近缺口做的小規模測試。結果見 `FINDINGS.md`。

## 為什麼判準那一欄比模型的輸出重要

`cwes.tsv` 的「答案」欄是整份實驗的判準，尤其是那七個「無」。
每一條「無」我都要說得出理由，理由寫在 `FINDINGS.md`，一律是打開檔案數過。

沒有這一步的話，「七類裡亂指五類」只是我自己挑了七個容易讓它出錯的類別。

## 描述那段字也不是我說了算

CWE-502 與 CWE-1333 這兩條，第一版的描述是我憑印象寫的。改成 cwe.mitre.org
那段 Description 的原文重跑之後，CWE-1333 的答案從「指 `server/tools.js`」翻成
「回答沒有」，而其餘十一條逐字相同。

所以描述的措辭會動搖成績。現在十三條全部逐字取自官方頁，`verify.sh` 第 7b 條
拿 `cwe-pages/` 的快照比對；第 7c 條比對兩份表（差異列的編號與欄位），
第 7d 條比對兩輪存檔。兩條分開是因為失敗診斷不同：7c 說「我改的不只描述」，
7d 說「變的不只那兩條」。
`cwes-firstdraft.tsv` 與 `hunt-firstdraft/` 就是換描述之前那一輪：

```bash
CWES_TSV=cwes-firstdraft.tsv python3 hunt.py "$ANTARES_MLX" hunt-firstdraft
```

## 為什麼要有改名對照組

`hunt.py --rename` 把七個檔名換成 `m1.js` 到 `m7.js`。少了這一組，
「它挑對了」有另一個解釋：它只是認得 `tools.js` 這個名字。

還有一組更省事的做法要排除掉：只給檔名清單、不給內容。檔名清單短得多，
幾百個檔的專案也塞得下，所以它很誘人。`names-only.py` 跑兩發問同一個 CWE-78：
真名那發答 `server/tools.js`（對），檔名換掉那發答 `server/m1.js`，
對回去是 `files.js`（錯）。這兩次的結果符合「模型受檔名影響」的解釋，
但只有一輪，不能把檔名寫成唯一原因。

**只給檔名時，模型沒有足夠證據判斷程式是否有洞。** 要它檢查內容，就得把內容給它。
這一組由 `verify.sh` 第 8b 條守著。

對照組有一處不乾淨，`FINDINGS.md` 那節有寫：`src/render.js` 第一行的 import
把 `api.js` 這個真名帶進去了。

## 候選清單不是發現

模型交出來的那個檔，`confirm.sh` 打開之後看到的是**兩個**入口，不是一個。
模型只說「這個檔要看」，它沒說有幾處，也沒說打不打得進去。

那支腳本的判準錯過兩次，兩次都是「通過其實什麼都沒證明」：

1. 第一版拿文字當證據，payload 出現在錯誤訊息裡就判成打進去了。但文字出現只能證明
   有程式把它印了出來，分不出它被當成參數，還是同時被 shell 當成指令執行。
   改成看檔案系統上有沒有生出標記檔才分得開。
2. 第二版只看「修好那半沒生出標記檔」，而那個結果有三種原因長得一樣：消毒成功、
   `dig`／`convert` 不在這台機器上、模組壓根沒跑。現在缺執行檔直接回 2，
   而且每個入口先用良性參數打一發，證明這條路徑真的把指令送出去了。

第二次是外審實測抓到的：把 PATH 換成沒有那兩支指令的版本，整支照樣通過。
兩次都是同一句話：**守行為，不守形狀**，而「沒有發生」不等於「被擋下來」。
